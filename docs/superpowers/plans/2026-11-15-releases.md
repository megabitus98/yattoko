# Releases Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every promote that moves `stable` becomes one SemVer release (git tag, image tag, GitHub Release), and the bot shows its version and tells the owners when it was updated.

**Architecture:** One bash "release rule" block (title pattern, `next_version`, `previous_tag`) is written identically into `ci.yml`'s `unit` job and `promote.yml`; `unit` bakes the computed version into the image, `promote` recomputes it, checks the image label and creates the tag and release. The bot reads the baked env vars, shows the version in `/about` and announces a new version once, keeping the last announced one in SQLite.

**Tech Stack:** GitHub Actions (bash, `gh api`, `docker buildx imagetools`), Dockerfile build args, Python 3.12, SQLAlchemy (SQLite), kurigram, pytest.

**Spec:** `docs/superpowers/specs/2026-11-15-releases-design.md`

## Global Constraints

- Title pattern, exactly: `^(feat|fix|deps|docs|ci|test|build|chore|refactor|perf)(\([a-z0-9-]+\))?(!)?: .+`
- Bumps: `!` → major (`vX+1.0.0`); `feat` → minor (`vX.Y+1.0`); every other type → patch (`vX.Y.Z+1`); no previous tag → `v1.0.0` whatever the type.
- Tags are `vX.Y.Z` only (`^v[0-9]+\.[0-9]+\.[0-9]+$`); "previous tag" = the highest such tag (by version) whose commit is the given commit or one of its ancestors.
- A job with a write token runs no action (`uses:`), checks out nothing and starts no container (existing rule, `test_write_tokens_never_run_pr_code`).
- The PR title reaches scripts only through `env:` or the API, never as `${{ ... }}` inside `run:`; it is passed between steps in a file under `$RUNNER_TEMP`, never through `$GITHUB_ENV`.
- Every changed source file keeps one `# Modified 2026 by megabitus98 (fork): ...` line under its header; extend it, do not add a second.
- No private details in the repository (no IPs, Telegram IDs, hostnames). Commits: noreply identity, no AI attribution trailer.
- `black` on changed Python files that were black-clean on `main`; do not reformat files that were not.
- Unit tests make no network calls.

## Review Focus

1. A PR title with quotes, `$(...)`, backticks or `;` must never run as code: it only travels in env vars and files (pinned by `test_pr_title_never_inline_in_run`, Task 1).
2. A promote re-run after a partial failure (image tagged, release missing; or everything done) must finish or no-op, never mint a second version (Task 2, step order + manual re-run in Task 5).
3. Near-miss titles (`Feat: x`, `feat:x`, `feature: x`, `fix(Scope): x`, empty) fail `unit` before the build with a message naming the pattern (`test_release_rule_rejects`, Task 1).
4. The first release is `v1.0.0` for any type, including `fix!:` (`test_release_rule_bumps`, Task 1).
5. Startup must never fail because of the announcement: a database error or unreachable owners is logged, not raised; a `dev` build never announces (`test_announce_*`, Task 4).

- [ ] **Step 3: Write the release-rule block** into `ci.yml` (and, in Task 2, unchanged into `promote.yml`). The algorithm, exactly:

```bash
# >>> release rule (identical in ci.yml and promote.yml; tests/repo/test_pipeline_files.py checks it)
title_pattern='^(feat|fix|deps|docs|ci|test|build|chore|refactor|perf)(\([a-z0-9-]+\))?(!)?: .+'
# next_version <previous tag or empty> <PR title>: the release this PR becomes; fails on an unknown title
next_version() {
  local previous=$1 title=$2 type breaking major minor patch
  [[ "$title" =~ $title_pattern ]] || return 1
  type=${BASH_REMATCH[1]}
  breaking=${BASH_REMATCH[3]}
  if [ -z "$previous" ]; then echo v1.0.0; return 0; fi
  IFS=. read -r major minor patch <<< "${previous#v}"
  if [ -n "$breaking" ]; then echo "v$((major + 1)).0.0"
  elif [ "$type" = feat ]; then echo "v$major.$((minor + 1)).0"
  else echo "v$major.$minor.$((patch + 1))"; fi
}
# previous_tag <commit>: the highest vX.Y.Z tag on that commit or one of its ancestors (empty: none yet).
# An API error fails (an empty answer would mean "no tags" and restart at v1.0.0); no tags at all is not an error.
previous_tag() {
  local all_tags tag_name tag_sha status
  all_tags=$(gh api --paginate "repos/$GH_REPO/tags" --jq '.[] | "\(.name) \(.commit.sha)"') || return 1
  while read -r tag_name tag_sha; do
    status=$(gh api "repos/$GH_REPO/compare/$tag_sha...$1" --jq .status) || return 1
    case $status in ahead|identical) echo "$tag_name"; return 0 ;; esac
  done < <(grep -E '^v[0-9]+\.[0-9]+\.[0-9]+ ' <<< "$all_tags" | sort -rV)
}
# <<< release rule
```

- [ ] **Step 4: Add the `Release version` step to `unit`**, directly after `actions/checkout`. `unit` permissions become `contents: read`, `pull-requests: read`, `actions: read`. Step env (step level only, not job level, so the test steps that run PR code get no token): `GH_TOKEN: ${{ github.token }}`, `GH_REPO: ${{ github.repository }}`, `pr_number: ${{ github.event.pull_request.number }}`. The step, in order:
  1. the release-rule block;
  2. `pr_title=$(gh api "repos/$GH_REPO/pulls/$pr_number" --jq .title)` (live, so a re-run after a title edit sees the new title);
  3. `base_sha=$(git merge-base HEAD refs/remotes/origin/main)`;
  4. wait while `gh api "repos/$GH_REPO/actions/workflows/promote.yml/runs?head_sha=$base_sha&per_page=20" --jq '[.workflow_runs[] | select(.status != "completed")] | length'` is not `0`, every 10 s, at most 90 times; after that fail with `::error::` naming `$base_sha`;
  5. `previous=$(previous_tag "$base_sha")` on its own line (so a failure stops the step; a failure inside an argument's `$(...)` would not), then `version=$(next_version "$previous" "$pr_title")` or fail with `::error::the PR title must match $title_pattern (feat: minor, fix:/deps:/... patch, type! major)`;
